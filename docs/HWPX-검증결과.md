## 지시한 6개 항목에 대한 답

1. **무수정 저장 보존**: 통과. 바꾸지 않은 항목은 로컬 헤더·압축 데이터·서술자를 그대로 복사한다. (`test/hwpx.test.ts`, `test/docx.test.ts`)
2. **삽입·삭제·교체와 id 보존**: 통과. 문단 단위 편집은 앞뒤 공통 글자를 보존하고 달라진 구간만 해당 글자 조각에서 바꾼다. 삽입은 앞 조각의 글자 모양을 따른다. 문단 `id` 목록 동일(`test/robustness.test.ts`).
3. **특수문자·한글·공백**: `& < > " '`, 한글, 이모지(서로게이트), 앞뒤·연속 공백은 왕복 통과. **줄바꿈·탭·XML 제어문자는 거부**한다(문단 나누기와 탭 요소 구현 전까지).
4. **개체 태그·z-order·메타태그·미리보기·수정 일시**: 편집하지 않는 부분은 바이트 그대로라 손상이 없다. 미리보기(`PrvText.txt`)와 수정 일시(`ModifiedDate`)는 **자동으로 갱신하지 않고** 호출자가 `syncPreviewText`, `touchModified`를 부를 때만 바꾼다(정책 선택 가능). 두 함수는 단위 시험을 통과했지만 한/글이 바뀐 미리보기를 어떻게 다루는지는 미확인.
5. **손상·잘못된 요청**: 아래 "수정한 결함" 참고.
6. **표 셀·여러 구역·머리말·꼬리말·각주**: 아래 표.

| 항목 | 상태 | 근거 |
|---|---|---|
| 표 셀 글자 | **실제 시료로 검증** | 한/글 시료의 셀 문단(`context=cell`) 편집·재열기 통과 |
| 글상자(`hp:drawText`) | 목록과 구분만 확인 | 시료 1개에서 `textbox`로 분류. 편집은 시험하지 않음 |
| 여러 구역 | **미검증** | 시료가 모두 구역 1개. 구역 정렬 코드는 있으나 시험 불가 |
| 머리말·꼬리말·각주·미주 | **합성 XML로 분류만 확인** | 실제 시료(한/글, rhwp 변환 모두)에 이 요소의 글자가 없음. 편집 시험 없음 |
| 줄 배치 캐시(`hp:linesegarray`) | **한/글 실측으로 결정함** | 기본 `drop`(편집한 문단의 캐시만 삭제). `keep`은 줄 수가 늘면 한/글에서 글자가 겹쳐 그려진다(아래 "한/글 2022 실측"). rhwp는 이 캐시를 쓰지 않아 두 정책을 구분하지 못했다 |

## 수정한 결함 (코드 검토에서 찾고 회귀 시험을 추가함)

| 결함 | 수정 | 시험 |
|---|---|---|
| `replaceText(all)`가 한 글자 조각 안의 두 번째 이후 일치를 바꾸지 않음 | 조각 안 모든 일치를 바꿈 | `replaceText` 시험 |
| `replaceText`의 치환 문자열에서 `$&` 같은 패턴이 해석됨 | 함수형 치환으로 글자 그대로 사용 | 같은 시험 |
| 빈 찾을 글자 허용 | `EditError` | 잘못된 요청 시험 |
| 자기닫힘 `<hp:p/>` 뒤 문단의 소속이 어긋남(스택이 안 닫힘) | 자기닫힘은 스택에 넣지 않음 | 자기닫힘 시험 |
| 줄바꿈·탭·제어문자·짝 없는 서로게이트를 그대로 XML에 씀 | 편집 전에 거부, 문서는 바뀌지 않음 | 거부 시험(바이트 동일 확인 포함) |

| `node:zlib` 사용으로 브라우저에서 실행 불가 | fflate(MIT)로 교체. 기존 34개 시험이 그대로 통과 | 전체 시험 |

## 한계

- 구조분석 3.4의 손실(`hp:p@id` 재번호 등)이 **일어나지 않음**을 확인했지만, 이는 우리가 문서를 다시 쓰지 않기 때문이다. 문단 나누기·글자 모양 변경 같은 구조 편집을 추가하면 새 문단 id, 새 charPr 정의가 필요하고, 그때 다시 시험해야 한다.
- 이번 시험의 "독립 검증"은 rhwp(MIT)와 파이썬 `zipfile`, xmldom이다. **한/글 프로그램은 이 환경에 없어 실행하지 않았다.**
- `hwpx-generated` 시료는 rhwp 출력이라 "한/글이 만든 HWPX"의 근거로 쓸 수 없다.

## E4·E5 시도 결과: 이 PC에서는 한/글 저장본을 분석할 수 없다 (2026-10-22)

**시도**: 한/글 2022에서 원본 nrich를 `다른 이름으로 저장하기`(HWPX 형식)로 저장하고, 빈 문서도 HWPX로 저장했다.

**관찰**: 두 파일 모두 첫 바이트가 ZIP(`PK`)이 아니라 `9B 20 44 52 4D 4F 4E 45 …` 이고, 머리글에 `This Document is encrypted and protected by Fasoo DRM`이 있다. 우리 ZIP 파서와 파이썬 `zipfile` 모두 읽지 못한다(`File is not a zip file`). 이 PC에는 `Fasoo DRM Client for JEJU 1.74.0002`와 Fasoo LiveUpdate Agent가 설치되어 있다. 따라서 **이 PC의 한/글이 저장하는 모든 문서에 DRM이 자동 적용되는 것으로 보인다**(해석: 설치 항목과 머리글에서 추론. DRM 정책 자체는 확인하지 않음).

**결론**
- E4(한/글 재저장 기준선)와 E5(요소 하나씩 만든 시료)는 **이 환경에서 수행할 수 없다.** 한/글이 만든 평문 HWPX를 얻을 방법이 없다.
- DRM을 해제하거나 우회하는 방법은 쓰지 않았다(기관 문서보안 정책이며 저작권법 제104조의2의 기술적 보호조치와도 관련됨. `법적-보안-검토.md`).
- 한/글이 **연 파일을 읽는 것**(E1~E3)은 영향이 없었다. 평문 파일을 여는 데는 DRM이 개입하지 않았다.

**부작용(기록)**: 첫 시도에서 단축키 `Alt+S`는 "다른 이름으로 저장"이 아니라 **"저장하기"**(다른 이름은 `Alt+V`)여서, 열어 둔 `verify-out/E1-nrich-application-original.hwpx` 복사본을 한/글이 DRM으로 덮어썼다. `fixtures/`의 원본에서 복사본을 복구했고(해시 일치 확인), DRM 파일은 `verify-out/hangul-resave-DRM/`로 옮겼다.

**앱 대응(구현·시험 완료)**: 사용자가 DRM 암호화 파일을 열면 형식을 알아보고 "문서보안(DRM) 암호화 파일은 열 수 없습니다. 이 앱은 문서보안을 우회하지 않습니다"라고 알리고 열기를 거부한다(`src/engine.ts`, 단위 시험 1개, e2e 4개 프로필).

**진행 방법(선택지)**
1. DRM이 없는 환경(개인 PC 등)에서 사용자가 만든 평문 HWPX를 제공 — E4·E5를 그대로 수행할 수 있다.
2. 기관이 승인한 DRM 비적용 절차가 있다면 그 절차로 만든 파일을 제공(해제 절차는 사용자가 수행).
3. 한/글 화면 확인만 계속(열기·표시, E1~E3 방식). 구조 분석은 불가.
