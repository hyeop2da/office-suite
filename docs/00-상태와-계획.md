## 2-2. 남은 작업 진행 (2026-10-22, 이어서)

"남은 작업들 완료시켜" 지시에 따라, §2-1에서 "알려진 한계"로 남겨둔 항목 중 실제로 풀 수 있는 두 가지를 처리했다. Word·Excel·한/글은 이번에도 **사용자 자신의 문서를 연 채 실행 중이어서(위원회 추천명단.xlsx, seoul-menu-3e.hwp)** 자동화 검증을 시작하지 않았다 — 기존 세션 규칙 그대로.

1. **DOCX `paragraphs().text`가 탭·줄바꿈을 반영하지 않던 한계를 해소.** `xml-scan.ts`의 `PartConfig`에 `markers`(형제 레벨 표시 요소 → 고정 글자) 필드를 추가하고, `scanXml`이 `w:tab`/`w:br`를 보통 글자 조각과 같은 `TextNode` 목록에 `hasChildren=true`(= 편집 잠금)로 넣게 했다. HWPX는 건드리지 않았다(`hp:tab`이 `hp:t` *안에* 중첩되는 다른 구조라 이 형제 레벨 메커니즘이 맞지 않음 — 기존 `richParagraphText` 전용 경로를 그대로 둠). 부수적으로 `TextPart.setParagraphText`의 검증 순서를 "전체 새 글자" 검사에서 "진짜 새로 들어오는 부분(diff의 insert)만" 검사하도록 바꿨다 — 그러지 않으면 탭이 이미 들어 있는 문단을 다른 자리에서 고칠 때마다 "이미 있던" 탭 때문에 거부되는 새 회귀가 생기기 때문이다. 탭을 직접 지우거나 덮어쓰는 편집은 여전히 거부된다(해당 조각이 `touched`에 걸리면 기존 잠금 검사가 그대로 작동). 신규 시험 2개(`test/docx-structure.test.ts`), 전체 148개 통과.
2. **XLSX 병합 셀 읽기·편집 보호.** `mergeCells`/`mergeCell`(OOXML 공개 요소) 파싱을 추가해 `XlsxDocument.mergedRanges(sheet)`로 범위 목록을 읽고, `cell()`이 반환하는 `CellView`에 `merged: { ref, anchor }`를 채운다. `setCell`은 병합 범위의 왼쪽 위(anchor) 칸이 아니면 거부한다(실제 Excel UI와 같은 동작 — 숨겨진 칸에 값이 들어가면 병합이 깨진 것처럼 보임). 병합 요소 자체는 지금까지처럼 `sheetData` 밖이라 건드리지 않으므로 보존은 원래부터 보장되어 있었다 — 이번에 더한 것은 "읽어서 노출"과 "잘못된 편집을 막는 것"이다. 시료에 병합 셀이 없어 OOXML 공개 스키마대로 합성 주입해 재현했다(디컴파일 아님). 신규 시험 3개(openpyxl 교차 검증 포함), 전체 151개 통과. 빌드 정상.

남은 한계(§7 갱신): HWP 쪽 수 불일치 원인(레이아웃 알고리즘 내부 — 코드 분석 필요, 미착수), 탭 폭(width) 한/글 실측 미검증(DRM으로 막힘), HWPX splitParagraph의 표·그림 미지원. 이번 두 항목(DOCX 스캐너, XLSX 병합 셀)의 한/글·Excel 실제 열기는 **미검증**(둘 다 사용자 자신의 문서가 열려 있어 자동화를 시작하지 않음).

## 2-3. 남은 작업 추가 진행 (2026-10-22, 같은 지시 이어서)

§2-1의 "알려진 한계" 5번(PPTX·XLSX의 탭·줄바꿈·문단 나누기 미착수)을 마무리했다.

1. **XLSX는 이미 되고 있었다**(확인만, 새 코드 없음): 칸 글자에 탭·줄바꿈 문자를 그대로 넣을 수 있다(SpreadsheetML도 `<t>`가 xsd:string). "문단 나누기"는 칸 단위 편집에 적용될 개념이 아니라서 해당 없음으로 정리.
2. **PPTX는 새로 구현**: `xml-scan.ts`의 `markers`를 `a:br`(PPTX)에도 적용하고, 전용 요소가 없는 탭은 `a:t`에 리터럴 문자로 쓰도록 `validateText`에 `allowTab` 옵션을 추가했다(HWPX·DOCX는 그대로 거부). `PptxDocument.insertLineBreak()`·`splitParagraph()` 신규 구현(ECMA-376 DrawingML 공개 규격만으로, 실행 파일 분석 없음). 신규 시험 7개(python-pptx 교차 검증), 전체 157개 통과.
3. **실제 버그 1건 발견·수정**: `validateText`의 탭 허용 분기가 일반 제어문자 거부 검사(`c < 0x20`)를 피하지 못해, 허용했어야 할 탭이 여전히 거부되고 있었다. python-pptx로 실제 파일을 왕복시키는 과정에서 드러남(추측이 아니라 재현된 오류).
4. **이번엔 PowerPoint가 비어 있어 실제로 열어 확인했다**(Excel·한/글은 여전히 사용자 문서로 막혀 자동화하지 않음). COM으로 두 편집본을 열어 **복구 경고 없이 정상 열림**을 확인했고, 삽입한 탭은 실제 공백으로, 삽입한 `a:br`은 PowerPoint 자신의 `TextRange.Text`에서도 U+000B(수직 탭)로 나타남을 확인했다(python-pptx의 합성이 아니라 PowerPoint 자체 동작임이 이번에 밝혀짐). 확인 후 PowerPoint는 정상 종료, 잔류 프로세스 없음.

자세한 내용은 `탭-줄바꿈-문단나누기.md` §7-5 참고.

## 2-4. 한/글·Word·Excel 실제 열기 (2026-10-23, 사용자가 한/글·Excel을 닫은 뒤)

사용자가 한/글·Excel을 닫아줘서, 그동안 "사용자 문서가 열려 있어 미룸"으로 남겨뒀던 검증을 모두 마쳤다(모두 우리가 만든 테스트 파일만 열었고, 저장 없이 닫음).

- **Excel**: 병합 셀(F1:G2)·탭·줄바꿈이 든 XLSX를 COM으로 열어 복구 경고 없이 정상 열림을 확인. 병합 범위·칸 값 모두 정확.
- **Word**: 탭·줄바꿈(`w:br`)·문단 나누기가 섞인 DOCX를 COM으로 열어 정상 열림을 확인. 탭·문단 경계·줄바꿈 모두 기대대로.
- **한/글 2022**: 탭(`hp:tab`)·줄바꿈(`hp:lineBreak`)이 섞인 HWPX를 COM으로 열고 **화면 캡처로 직접 확인** — 탭 간격, 줄바꿈 둘 다 자연스럽게 표시됨. 이걸로 §7(2번, 탭 폭 미검증)을 해소했다.

이로써 이번 라운드(탭·줄바꿈·문단 나누기, DOCX 스캐너, XLSX 병합 셀, PPTX 신규 기능)의 **한/글·Word·Excel·PowerPoint 네 앱 모두 실제 열기 확인을 마쳤다.** 남은 미검증은 HWP 쪽 수 불일치 원인(§3, 코드 분석이 필요해 범위 밖으로 남겨둠)뿐이다. 자세한 내용은 `탭-줄바꿈-문단나누기.md` §7-6.
