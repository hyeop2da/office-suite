# 모바일 웹앱 아키텍처 (확정안, 2026-10-22)

대상: Android Chrome, iOS Safari(iPhone·iPad)에서 접속해 쓰는 반응형 웹앱. 설치형·PC 프로그램이 아니다. 이전의 "PC 스위트" 지시는 중단되었고 이 문서가 기준이다.

## 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 언어 | TypeScript. 기존 코어와 같은 언어 | 전면 재작성 없이 `src/*.ts`를 그대로 브라우저로 번들 |
| 번들 | esbuild(MIT), IIFE 한 파일(약 36KB), 대상 `chrome100`, `safari15` | 의존성이 가볍고 빌드가 즉시 끝남 |
| 런타임 의존성 | fflate(MIT) 하나 | Node와 브라우저에서 같은 압축 코드를 쓰려고 `node:zlib` 대신 사용 |
| 처리 위치 | **전부 브라우저 안.** 서버 없음, 업로드 없음 | 개인정보, 비용 0 |
| 서버 | 정적 파일만 필요(어떤 정적 호스팅도 가능) | 서버가 필요한 기능은 없다 |
| 저장 | 사용자가 고른 파일을 읽고, 수정본을 Blob 다운로드 | iOS는 파일 제자리 저장 불가. 다운로드 폴더로 내보낸다 |
| 임시 보존 | IndexedDB(키 하나). 화면에 안내문과 끄기·삭제 버튼 제공 | 새로고침·종료 대비. 개인정보 고지 포함 |

## 계층

```
web/index.html, web/app.css          화면(반응형, 안전 영역, 키보드 대응)
src/app/main.ts, draft.ts            UI 로직, IndexedDB 임시 보존
src/session.ts                       편집 세션: 수정 목록 → 저장 → 재열기 검증
src/engine.ts                        형식 판별, DocumentEngine 인터페이스, 지원 표시
src/hwpx.ts   src/docx.ts            형식별 코어(문서 처리, UI 모름)
src/text-part.ts, xml-scan.ts        무손실 글자 편집기, 위치 기반 XML 스캐너
src/zip.ts                           무손실 ZIP
```

- UI는 `DocumentEngine`(문단 목록, 문단 글자 바꾸기, 저장)만 안다. 새 형식은 엔진을 하나 더 등록하면 된다.
- 세션은 원본 바이트를 바꾸지 않고, 문단별 수정 목록을 쌓았다가 **저장할 때 원본에 한 번에 적용**한다. 되돌리기는 목록에서 빼면 끝난다.
- 저장하면 만든 파일을 다시 열어 모든 문단 글자를 비교하고, 실패하면 내려받지 않는다.

## 모바일 요구사항 반영 상태

| 요구 | 상태 |
|---|---|
| 세로·가로·태블릿 반응형 | 구현. 375×812, 768×1024에서 브라우저 창(Chromium 에뮬레이션)으로 확인 |
| 도구 모음 가림 | 도구 모음 높이를 `ResizeObserver`로 재서 본문 아래 여백에 반영(좁은 화면에서 줄이 늘어나 마지막 문단이 가려지던 결함을 자동 시험이 찾아 수정) |
| 터치·가상 키보드 | 글자 입력은 `<textarea>`(OS 키보드·IME 사용), 글꼴 16px(iOS 확대 방지), 도구 모음은 `visualViewport`로 키보드 위에 유지. **실제 기기 미검증** |
| 파일 선택·다운로드 | `<input type=file>` + Blob 다운로드. **실제 기기에서 다운로드 폴더 저장은 미검증** |
| 대용량 | 100MB 초과 거부, 30MB 초과 경고, 문단 150개씩 나눠 그림. 전체 파일을 메모리에 올리므로 상한은 기기 의존 |
| 새로고침 대비 | IndexedDB 임시 보존 구현, 같은 브라우저에서 "이어서 하기" 확인 |
| 서버 보안·보존 정책 | 서버가 없어 해당 없음. 서버를 도입하면 별도 설계 필요 |
| 확대·축소 | 브라우저 기본 핀치 확대에 의존. 문서 레이아웃 렌더링은 아직 없음 |
| 보안 | CSP로 외부 스크립트·연결 차단(`script-src 'self'`), 문서 글자는 `textContent`로만 표시. `style-src`에는 `'unsafe-inline'`을 허용했다: WebKit이 `<input type=file>` 내부 스타일을 막아 콘솔 오류를 내서다(자동 시험에서 발견). 스크립트 보호에는 영향 없음 |

## 오프라인과 홈 화면 추가 (구현됨)

- `web/sw.js`를 빌드가 파일 목록·내용 해시 버전으로 채워 `dist/sw.js`로 만든다. 설치 때 앱 파일(코드, 화면, 샘플, 매니페스트, 아이콘) 17개를 캐시하고, 보기 엔진(rhwp WASM, pdf.js 작업자, 한글 글꼴 맵)은 **처음 쓸 때** 받아 캐시한다. 화면 이동은 온라인이면 네트워크 우선, 오프라인이면 캐시된 첫 화면.
- **사용자 문서는 캐시하지 않는다**(시험으로 확인: 캐시 URL에 사용자 파일이 없고 모두 같은 출처). 임시 보존은 이전처럼 IndexedDB.
- 새 빌드는 새 캐시 이름을 쓰고 옛 캐시를 지운다. iOS 홈 화면 추가(`apple-touch-icon`, `display: standalone`)는 **실기기 미확인**.

## 쪽 미리보기 (구현됨, 읽기 전용)

- rhwp(MIT, WASM 약 11.8MB)는 **"쪽 보기"를 누를 때만** 내려받는다(번들은 ESM 코드 분할, 첫 화면 JS 약 40KB). CSP에 `'wasm-unsafe-eval'`과 `img-src blob:`를 추가했다.
- 쪽은 SVG를 `<img>`(blob URL)로만 넣는다(이미지 안 스크립트는 실행되지 않음). 3쪽씩 더 보기.
- HWPX는 **저장 때와 같은 검증을 거친 현재 편집본**을 그린다. HWP(바이너리)는 원본을 읽기 전용으로만 그린다(편집·저장 없음).
- 한계: 글꼴과 줄바꿈이 한/글과 다를 수 있다. 쪽 수는 HWPX 5개 모두, HWP 5개 중 4개가 한/글과 일치했다(briefing 25쪽 대 26쪽).

## (이전 서술) 왜 문서 레이아웃 화면이 없었는가

지금 화면은 "문단 목록 편집기"다. 쪽 배치 표시는 rhwp 렌더러(MIT, WASM)를 읽기 전용으로 붙이는 다음 단계다. rhwp는 저장 경로에 쓰지 않는다.
