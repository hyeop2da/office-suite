## 3. 재현에 성공한 결과 (새 비교 도구 `src/xmldiff.ts`, 시험 `test/reproduce-prior.test.ts`)

이전 보고서의 rhwp 저장 손실 수치를 **독립적으로 다시 구현한 도구**로 5쌍 모두에서 센 결과:

| 이전 주장 | 재현 |
|---|---|
| 문단 `hp:p@id` 재번호(81, 58, 100, 100, 301건) | **재현됨** |
| `hp:t` 요소 수 변화(56→82, 102→110, 212→238, 65→101, 165→362)와 빈 `hp:t` 수 | **재현됨** |
| `hh:paraPr@textDir` 16건 손실(nrich) | **재현됨** |
| `hp:subList@metatag` 12건, `hp:metaTag` 1→0, `hp:fieldBegin@zorder` 1건 손실(pipc) | **재현됨** |
| `hh:strikeout@shape` 3D→NONE 2건(pipc) | **재현됨** |
| content.hpf 항목 id·href·media-type 변경 6건, `linear` 변경(pipc) | **재현됨** |
| version.xml 압축 방식이 STORED→DEFLATE | **재현됨** |
| 바이트 동일 항목 수 | rhwp 저장본은 **어떤 항목도 압축 바이트까지 같지 않음**(원본 대비 0개) |

**정정할 것**
1. 이전 보고서는 "ZIP 엔트리 순서가 5쌍 모두 바뀌었다"고 썼다. **공통 항목의 상대 순서가 바뀐 것은 3쌍**이고, 나머지 2쌍(manual, spec)은 `Preview/PrvImage.png`가 새로 끼어든 것이다.
2. `opf:item@isEmbeded` "손실 2, 추가 2"는 항목 순서가 바뀐 탓에 위치 기반 짝짓기가 어긋난 **도구 한계**일 가능성이 높다(우리 도구도 같은 값을 냄). 의미 있는 손실로 보지 않는다.
3. 이 재현은 **파일 구조의 차이**이지, 한/글에서 열었을 때 문제가 되는지는 여전히 모른다.

**우리 편집 코어에 같은 비교를 적용**: 글자 한 군데 편집 후 바뀐 ZIP 항목은 `section0.xml` 하나, 요소 수·속성 변화 0, 순서·압축 방식 변화 0, 나머지 항목은 압축 바이트까지 동일(5개 시료 모두).

## 4. 새로 확인한 시료 사실

- **HWP 5.x 시료**(`tools/hwp_inspect.py`, olefile): 버전 5.0.3.4 ~ 5.1.1.0, 플래그는 모두 "압축"만(암호·배포용·DRM 없음), 구역 1개. rhwp 저장본은 첫 구역의 레코드 수, 문단 텍스트 수, 표 수가 원본과 같다. 압축 해제한 구역 크기는 마커 때문에 14바이트(2개 파일) 또는 50바이트(3개 파일) 늘었고, **50바이트의 36바이트 차이는 원인을 분석하지 않았다**.
- **시료 적합성**(`tools/inventory.ts`): 한/글이 만든 5개에는 머리말, 꼬리말, 각주, 미주, 책갈피, 수식, OLE, 탭, 줄바꿈, 자동 번호, 변경 추적, 여러 단, 묶음 개체, **하이퍼링크가 없고**, 구역은 모두 1개다. 그림·글상자·누름틀·쪽 번호는 pipc 1개에만 있다. 따라서 이 기능들의 저장 보존은 **시험할 수 없다.** `test/analysis-tools.test.ts`가 이 공백을 못 박아 두었다.
