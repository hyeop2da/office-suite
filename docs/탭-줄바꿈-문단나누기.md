# 탭·줄바꿈·문단 나누기 구현 (2026-10-22)

## 1. 확인된 사실(시작 시점)

- HWPX·DOCX 글자 편집은 되어 있었지만(`text-part.ts`), 탭·줄바꿈·문단 나누기는 **입력 단계에서 거부**했다(`validateText`가 `\t`/`\n`을 전부 EditError로 막음). `docs/기능대응표.md`에 "미구현"으로 적혀 있었다.
- HWP 쪽 수 불일치(assembly-briefing: rhwp 25쪽 vs 한/글 26쪽)는 재현 가능한 오류지만, 원인이 레이아웃 계산(재조판 알고리즘) 내부에 있어 **파일 구조 비교로는 "왜 1쪽 차이 나는가"에 답할 수 없다** — 분석 방법별 판단표에서 "구조 비교로 안 되고, 코드 분석이 필요한" 쪽으로 분류했다.
- XLSX 병합 셀·DOCX 서식 심화는 급하지 않다고 판단해 이번엔 다루지 않았다(미해결로 유지).

## 2. 분석 방법별 판단

| 방법 | 이번에 한 일 | 비고 |
|---|---|---|
| 메타데이터·구조 확인 | `fixtures/hwpx-generated/assembly-briefing.hwpx`(rhwp로 실제 HWP를 변환한 실물 파일)에서 `hp:tab`·`hp:lineBreak`의 실제 XML 모양을 직접 읽음 | 실행 파일이 아니라 **우리가 가진 MIT 라이선스 도구(rhwp)로 우리 시료를 변환한 결과물**을 읽은 것. 디컴파일이 아님 |
| 정적 디스어셈블·디컴파일 | **하지 않음** | 이전 대화에서 확정한 이유(법적 불확실성) 그대로. 이번 문제(탭·줄바꿈·문단 나누기)는 공개 규격(OOXML)과 실물 샘플(HWPX)만으로 충분히 풀렸다 — 시도 자체가 불필요했다 |
| 동적 분석(디버깅) | 하지 않음 | 해당 없음 |
| 공개 규격 | ECMA-376(OOXML)의 w:tab·w:br가 w:r 안에서 w:t와 형제 요소로 올 수 있다는 것은 공개 지식. HWPX는 공개 규격 문서를 갖고 있지 않아(유료) 실물 샘플 관찰로 대체 | |

**결론**: 이번에 실제로 필요했던 기술 정보(탭·줄바꿈의 XML 표현)는 실행 파일을 보지 않고 **우리가 이미 가진 도구와 공개 규격**으로 얻었다. "실행 파일 분석이 필요한가"를 먼저 판단하지 않고 실제로 시도한 결과, 필요하지 않았다 — 이건 선입견이 아니라 이번 작업의 실적이다.

## 3. 실제로 관찰한 것 (fixtures/hwpx-generated/assembly-briefing.hwpx)

```xml
<hp:t>※ 금주 2026년도 국정감사 일정<hp:tab width="1496" leader="0" type="1"/><hp:tab width="4000" leader="0" type="1"/>...</hp:t>
```

- `hp:tab`은 **hp:t 안에 중첩**된다(글자와 같은 레벨). `width`는 1496~51024로 위치마다 다르다 — 실제 배치 계산값으로 보이지만, 그 계산 방법은 코드 분석 없이는 알 수 없다. **그래서 새로 넣는 탭은 샘플에서 가장 흔했던 `width="4000"` 고정값을 쓴다. 한/글이 이 폭을 그대로 쓰는지, 다시 계산하는지는 미검증이다.**
- `hp:lineBreak`는 속성 없는 자기닫힘 요소.
- DOCX는 OOXML 공개 규격대로 `w:tab`/`w:br`가 **w:t와 형제**로 `w:r` 안에 온다(hp:t 안에 중첩되는 HWPX와 구조가 다르다). 이 차이를 그대로 설계에 반영했다.

## 4. 구현한 것과 코드 위치

| 기능 | HWPX | DOCX |
|---|---|---|
| 탭·줄바꿈이 섞인 문단 읽기 | `HwpxDocument.richParagraphText()` | (기존 `paragraphs()`는 탭·줄바꿈을 `.text`에 반영하지 않음 — §6 한계 참고) |
| 탭·줄바꿈을 포함한 자유 편집 | `HwpxDocument.setParagraphRichText()` | 해당 없음(구조가 달라 자유 편집 대신 전용 메서드로) |
| 탭 삽입 | 위와 같음(\t 입력) | `DocxDocument.insertTab()` |
| 줄 안 줄바꿈 삽입 | 위와 같음(\n 입력) | `DocxDocument.insertLineBreak()` |
| 문단 나누기 | `HwpxDocument.splitParagraph()`(본문만, run/t/linesegarray/lineseg만 있는 단순 문단) | `DocxDocument.splitParagraph()`(하이퍼링크·그림·필드·탭·줄바꿈이 없는 단순 문단, w:pPr 양쪽에 복제) |

공통 하부 구조:
- `src/xml-scan.ts`: `findElementSpan`(중첩 고려 여는/닫는 태그 짝 찾기), `onlyTags`, `lastTagOpenBefore`(태그 이름 경계 정확한 역방향 검색) — 재사용 가능한 구조 탐색 도구.
- `src/text-part.ts`: `TextPart.applyRawEdits()` — 호출자가 계산한 여러 구간을 한 번에 적용하는 저수준 API. 기존 `setText`/`setParagraphText`는 전혀 바꾸지 않았다(회귀 위험 0).

## 5. 찾아서 고친 버그 2건 (구현 중 시험이 발견)

1. **DOCX 문단 나누기에서 `<w:r` 역방향 검색이 `<w:rPr>`와 충돌**: `xml.lastIndexOf('<w:r', pos)`가 `<w:rPr>` 여는 태그의 4글자 접두사(`<w:r`)에 걸려 run의 진짜 시작 위치를 못 찾고 깨진 XML을 만들었다(서식 있는 런을 나눌 때만 드러남 — `lxml.etree.XMLSyntaxError: Opening and ending tag mismatch`로 python-docx가 바로 잡아냄). `lastTagOpenBefore()`(태그 이름 뒤 경계 확인)로 교체해 고쳤다.
2. **문단 나누기가 경계에서 정확히 나뉠 때 서식만 있고 글자가 없는 빈 run을 남김**: 예를 들어 "굵게|보통" 두 런 경계에서 나누면, 빈 쪽에도 굵게 서식(`w:rPr`)만 있는 빈 `<w:r>`가 생겼다(불필요하지만 깨진 건 아님). 글자가 빈 쪽은 run 자체를 만들지 않도록 고쳤다.

## 7. 알려진 한계(분석하지 못한 부분과 이유)

1. ~~**DOCX `paragraphs()`의 `.text`가 탭·줄바꿈을 반영하지 않는다.**~~ **2026-10-22 해소.** `xml-scan.ts`의 `PartConfig.markers`(형제 레벨 표시 요소 → 고정 글자)를 추가해 `w:tab`→`\t`, `w:br`→`\n`이 보통 글자 조각과 함께 `paragraphs().text`에 보이도록 했다(`hasChildren=true`로 표시해 그 구간은 여전히 자유 편집으로 고칠 수 없게 잠가 둠 — 탭을 지나치는 편집은 거부됨). HWPX는 그대로 두었다(`hp:tab`이 `hp:t` *안에* 중첩되는 다른 구조라 이 형제 레벨 메커니즘이 맞지 않음). `TextPart.setParagraphText`의 검증도 "전체 새 글자"가 아니라 "diff로 걸러낸, 진짜 새로 들어오는 부분"만 보도록 바꿔, 이미 탭이 있는 문단을 다른 자리에서 고칠 때 생길 뻔한 새 회귀를 막았다. 자세한 구현은 `test/docx-structure.test.ts`의 "paragraphs().text" 시험 참고. 다른 125개 기존 시험에 회귀 없음(148개 전체 통과).
2. ~~**삽입한 탭의 폭(width)이 한/글에서 맞는지 미검증.**~~ **2026-10-23 화면으로 확인.** §7-6 참고 — 고정값(4000)이 한/글 2022에서 자연스러운 탭 간격으로 보인다. 다만 이건 "보기에 이상 없다"는 확인이지, 한/글이 내부적으로 이 값을 그대로 쓰는지 다시 계산하는지(예: 다른 글꼴·자간에서도 같은 결과인지)까지 코드 수준으로 확인한 것은 아니다 — 그러려면 레이아웃 계산 코드를 봐야 하므로(=디컴파일 없이는 불가) 여전히 범위 밖이다.
3. **HWP 쪽 수 불일치 원인은 여전히 모른다.** 이번에 다루지 않았다. 레이아웃 알고리즘 내부를 봐야 하는 문제라 구조 비교로는 풀리지 않고, 코드 분석의 법적 불확실성은 이전 대화에서 정리한 그대로 남아 있다.
4. **HWPX splitParagraph는 표·그림·컨트롤이 있는 문단을 지원하지 않는다**(의도적 제한, 거부 시험으로 확인). DOCX splitParagraph도 하이퍼링크·그림·필드가 있으면 거부한다.
5. ~~**PPTX·XLSX의 탭·줄바꿈·문단 나누기는 다루지 않았다**~~ **2026-10-22 해소.**
   - **XLSX는 이미 지원하고 있었다**(새 코드 없음, 확인만 함): 칸 글자 값에 탭(U+0009)·줄바꿈(U+000A) 문자를 그대로 넣을 수 있다 — `checkInput`이 둘 다 통과시키고, `<t>` 내용에 리터럴 바이트로 그대로 써도 유효한 XML(ECMA-376 SpreadsheetML도 xsd:string). "문단 나누기"는 칸에 적용될 개념이 아니다(한 칸 = 한 문단처럼 다루면 됨). openpyxl 교차 검증으로 재확인(`test/xlsx.test.ts`의 기존 "줄바꿈·이모지 왕복" 시험).
   - **PPTX는 새로 구현했다**: ECMA-376/ISO 29500 DrawingML(공개 규격) 확인 결과 `a:p`가 허용하는 자식은 `a:pPr?, (a:r|a:br|a:fld)*, a:endParaRPr?` 뿐이다. 탭은 전용 요소가 없어(HWPX `hp:tab`·DOCX `w:tab`과 다름) `a:t`(xsd:string)에 문자 그대로 쓴다(스키마로 확인한 결론, 실행 파일 분석 없음). 줄 안 줄바꿈은 `a:br`인데 **`a:r`의 형제**로 온다(DOCX의 `w:br`이 `w:r` *안의* `w:t`와 형제인 것과 다른 구조) — 그래서 그 위치의 런을 둘로 쪼개고 사이에 끼운다(서식 양쪽 복제). 문단 나누기는 `a:p`를 통째로 나눈다(`a:pPr` 복제, 끝의 `a:endParaRPr`은 뒤쪽 문단에 남김). python-pptx로 교차 검증: `a:br`은 `paragraph.text`에서 `\v`(U+000B)로 합성되어 보인다는 것을 실측으로 확인(이 합성 방식은 python-pptx 자체 동작이며, 우리 코드와는 무관). 신규 시험 7개(`test/pptx.test.ts`), 전체 157개 통과. 필드(`a:fld`)가 있는 문단은 여전히 거부(보수적 설계).
   - 이 작업 과정에서 **실제 버그 1건**을 찾아 고쳤다: `validateText`의 탭 허용(`allowTab`) 분기가 탭 전용 거부 검사만 건너뛰고, 뒤따르는 일반 제어문자 검사(`c < 0x20`)에는 걸려 여전히 거부되고 있었다(0x09도 0x20보다 작으므로). `if (c === 0x09) { 탭 거부 검사 } else if (c < 0x20 ...)` 형태로 고쳐, 허용된 탭은 두 검사 모두 건너뛰게 했다. python-pptx로 실제 파일을 열어 읽어보는 과정에서 발견됨(추측이 아니라 실패 재현).
   - **PowerPoint 2024(LTSC, 설치됨)에서 실제 열어 확인함**(이번에는 PowerPoint가 비어 있어 COM 자동화 가능 — Excel·한/글만 사용자 문서로 막혀 있었음). COM(`Presentations.Open`)으로 두 편집본을 열었고 **둘 다 복구 경고 없이 정상 열림**:
     - 탭+문단 나누기 편집본: `TextRange.Text`가 `"첫<TAB>째 줄"`로, 삽입한 탭이 실제 공백 문자로 보존됨을 확인.
     - 줄바꿈(`a:br`) 편집본: `TextRange.Text`가 그 자리를 **U+000B(수직 탭)로 보여줌** — python-pptx가 합성한 것과 똑같은 문자다. 즉 이건 python-pptx만의 동작이 아니라 **PowerPoint 자신이 `a:br`을 그렇게 표현한다**는 뜻이다(COM API로 실측, 디컴파일 아님).
     - 문단 나누기 뒤 문단 수를 COM `TextRange.Paragraphs(1,-1).Count`로 재려 했으나 이 호출이 매번 1을 반환해(COM API 특이 동작으로 보임, 원인 미분석) 그 경로로는 세지 못했다 — 문단 수는 이미 python-pptx(`test/pptx.test.ts`)로 충분히 확인했으므로 더 파지 않았다.
     - 확인 후 PowerPoint 프로세스를 정상 종료(`Quit`)했고 잔류 프로세스 없음을 확인함.

## 7-6. 한/글·Word·Excel 실제 열기 (2026-10-23, 사용자가 한/글·Excel을 닫은 뒤 실시)

이전까지 "사용자 자신의 문서가 열려 있어 자동화하지 않음"으로 미뤄뒀던 검증을 사용자가 두 앱을 닫은 뒤 진행했다. 모두 **우리가 직접 만든 테스트 파일**만 열었고(사용자의 실제 문서는 건드리지 않음), 확인 뒤 저장 없이 닫았다.

| 앱 | 방법 | 결과 |
|---|---|---|
| **Excel** (LTSC 2024) | COM(`Workbooks.Open`)으로 병합 셀(F1:G2)·탭·줄바꿈이 든 XLSX를 엶 | **복구 경고 없이 정상 열림.** `Range("F1").MergeArea.Address()` = `$F$1:$G$2`(정확), `Range("G1").MergeCells` = `True`, 탭·줄바꿈이 든 칸도 리터럴 문자로 올바르게 읽힘 |
| **Word** (LTSC 2024) | COM(`Documents.Open`)으로 탭·줄바꿈(`w:br`)·문단 나누기가 섞인 DOCX를 엶 | **복구 경고 없이 정상 열림.** 각 문단의 `Range.Text`를 확인: 탭이 실제 공백으로, 문단 나누기가 정확한 경계("앞" / "뒤 공백이 있는 문단")로, `w:br`이 U+000B(수직 탭)로 나타남 — **Word도 PowerPoint·python-pptx와 같은 방식으로 줄 안 줄바꿈을 표현한다**(공통 관례임을 이번에 확인) |
| **한/글 2022** | COM(`HWPFrame.HwpObject`)으로 탭(`hp:tab`)+줄바꿈(`hp:lineBreak`)이 섞인 HWPX를 엶. `GetTextFile("TEXT")`는 줄 안 줄바꿈을 구분 없이 이어 붙여(형식 자체의 한계로 보임) 판단에 못 썼지만, **실제 창을 화면으로 캡처해 눈으로 확인**: "[별지 제1호의 4서식]" 뒤에 탭 간격을 두고 "TAB확인"이 같은 줄에, "줄바꿈확인"이 **그 다음 줄에 문단 구분 없이** 자연스럽게 보임 | **정상 열림, 화면에 올바르게 표시됨.** 이걸로 §7-2의 "탭 폭 미검증"을 해소했다 |

세 앱 모두 자동화 뒤 프로세스가 정상 종료되었고 잔류 프로세스 없음을 확인했다(`Get-Process`로 재확인). 이로써 이 문서의 "한/글·Word 실제 열기 미검증" 항목은 모두 해소되었다 — 남은 미검증은 §7-3(HWP 쪽 수 불일치 원인, 코드 분석 필요)뿐이다.
